# i18n.parity

A page exists in one language but not in another that its hreflang set declares, and the site has not listed it as intentionally untranslated.

## Why it matters

An hreflang set says these pages are the same page in different languages. When the German home page promises an English twin and the build never emits one, the set lies: search engines drop the whole alternate group, visitors who click a language link land on a 404, and an agent that crawls the declared languages finds a different page count per language. Parity is what makes a multilingual site trustworthy: every page in every declared language, or a declared reason why not.

## What it checks

Pages are grouped into **alternate clusters** from the hreflang graph, the same way `i18n.hreflang` and `i18n.x-default` read it: a page joins a cluster when it declares a `rel="alternate" hreflang=...` entry whose `href` resolves to another page of this build, or when another page's language entry points at it. Linked pages merge transitively, so one connected set of mutual declarations is one cluster. `x-default` entries name a fallback page, not a translation: they never join a cluster, are never a language the set must serve, and a page named only as an `x-default` target stays outside.

For each cluster, the **declared languages** are the union of the `hreflang` values across its members (compared without regard to case, so `DE` and `de` are one language). A language is **served** when some member page has it as its own `<html lang>`, or declares a self-referencing entry (`hreflang="de"` pointing at the serving page itself). A language whose entries all point outside this build is declared to live on another host: Seaworthy verifies built output offline and never demands it here. One warning is reported per cluster and language with no page serving it, at the first page (by path) that declares that language. A cluster with one language asks for no translation, so monolingual sites report nothing.

## How to fix

```html
<!-- before: /about.html promises a German version the build never emits -->
<link rel="alternate" hreflang="en" href="/about.html">
<link rel="alternate" hreflang="de" href="/de/about.html">
<!-- after: build the missing page and let it declare the set back -->
<!-- /de/about.html -->
<link rel="alternate" hreflang="de" href="/de/about.html">
<link rel="alternate" hreflang="en" href="/about.html">
```

Create the missing translation in the source your generator translates from (template, i18n plugin, or content tree), so every page of the set gains the new entry and the new page declares the reciprocal links back. When the page will stay untranslated on purpose — a legal notice kept in one language, say — declare that instead of shipping an empty stub, using the option below; deleting the dangling `hreflang` entry from the set is the other honest fix.

## Options

Under `checks."i18n.parity".options`, the check accepts `untranslated`: an object mapping a language code to a list of page paths (site-relative, as findings spell them, with or without a leading `/`) the site declares intentionally untranslated. Naming any page of a cluster under a language opts that cluster and language out, silently.

```json
{
  "checks": {
    "i18n.parity": { "options": { "untranslated": { "de": ["legal.html", "press.html"] } } }
  }
}
```

A value that is not an object turns the option off; a language whose entry is not a list is ignored, and non-string paths inside a list are skipped; an unknown language key is simply never referenced. Nothing is rejected at the check: the config layer owns config errors, and a malformed option degrades quietly to "no opt-out", exactly like `quality.page-weight`'s `budgets`.
