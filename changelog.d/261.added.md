The Seaworthy Action can keep its run history between runs: a new `cache` input (`off` by default, `history` to turn it on) restores and saves `.seaworthy/history`, the run summaries `verify` records, with `actions/cache`, so a workflow has previous runs to trend and diff against instead of starting from nothing on every runner. The entry is keyed on the operating system, the ref that triggered the run, this Action's own ref, and a digest of the workspace `seaworthy.config.json`, and it is restored with no `restore-keys`: another branch, another configuration, or another build of the Action gets another store, never this run's baseline. What the cache hands back is then checked against the store's own fields before the CLI reads it — a record for a different site folder, or written by a newer history spec, is deleted rather than trusted, so a pull request run cannot report a false delta against main's history. Nothing else is cached: not the site, not the reports, not `node_modules`, not `.seaworthy/cache.json` (the `--changed` hashes carry no tool version, so a restored one could mark a file unchanged against a build that added a check for it), and not a browser — Seaworthy never downloads one, so there is none to keep. A cache miss, an unusable key, and an `actions/cache` failure all leave the verdict alone: it is still the verify CLI's exit code. (#261)
