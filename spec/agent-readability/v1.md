# Agent-readability spec, v1 (draft)

**Status:** Draft, 2026-10-18. Becomes frozen when the checks in it ship in `verify 0.1.0`. Task: `readability.spec`.

This spec says which published standards Seaworthy checks to answer "can agents and AI search read this site?", which rule it applies to each, which check ID reports it, and how severe a finding may be. It does not invent a format. Every check is anchored to a standard or a draft named below.

## Principles

1. **Standards only.** A check exists because a published document defines what is correct. If the document is a draft, the check says so in its message and docs page, and its findings are never errors.
2. **Absence is not a defect unless the standard requires it.** Most of these files are optional. The checks validate files that are present. A missing file is reported only where noted, and only at note level. A site can ask for stricter treatment in its config (`"expect": ["readability.llms-txt"]` raises "missing" to a warning); that option is reserved and not part of v1.
3. **Built output only.** Every check in this spec reads the built folder, except `readability.markdown-negotiation`, which needs a deployed URL and is opt-in.
4. **Honest severities.** See the severity table. `llms.txt` and everything defined by a draft stay at note or warning.
5. **Findings are actionable.** Each has a location (file, line, and column when the format allows) and a fix hint.

## Severity policy

| Situation | Highest severity |
| --- | --- |
| Optional file is absent | note |
| File defined by a stable standard (RFC) is present and invalid | warning |
| File defined by an informal proposal or a draft is present and invalid | warning |
| File is well-formed but a recommended field is missing | note |
| Content cannot be read without JavaScript | warning |
| A directive contradicts another on the same site | warning |
| Anything in this spec | never `error` |

These rules are enforced by tests (`packages/verify/tests/readability-policy.test.ts`): no `readability.*` check defaults to `error`, none produces an error on any fixture, the table below lists exactly the registered checks, and every docs page says that absence or severity is deliberate.

`error` is reserved for correctness checks whose standard is final and whose violation breaks consumers: broken links, invalid sitemaps, missing page language. This spec's checks never use it.

Each check's docs page (`docs/checks/<id>.md`) links the exact version it follows. When a draft changes, the check changes in a minor release and the docs page records the date.

## Checks

| Check ID | Applies to | Input | Severity (highest) | What it reports |
| --- | --- | --- | --- | --- |
| `readability.llms-txt` | `/llms.txt`, `/llms-full.txt` | built files | warning; note when absent | Missing file (note). File has no H1; a list item that is not `- [name](url)` with optional `: notes`; a link to a page that is not in the site; an H2 named "Optional" that holds non-list content |
| `readability.md-alternates` | every HTML page | built files | warning | A `rel="alternate" type="text/markdown"` link whose target is missing; a Markdown copy whose text shares too little with the page |
| `readability.jsonld` | every HTML page | built files | warning; note for recommended fields | `application/ld+json` that does not parse; no `@context`; a known type missing the fields consumers need (see its docs page) |
| `readability.ai-robots` | `/robots.txt` | built files | warning | AI crawler group with contradictory rules; a misspelled AI crawler name; `llms.txt` published while the whole site is closed to every known AI crawler |
| `readability.ssr-content` | every HTML page | built files | warning | Content that exists only after JavaScript runs: an empty application root and almost no text in the HTML |
| `readability.content-signals` | `/robots.txt` | built files | warning (Content Signals); note (AIPREF) | `Content-Signal:` lines with unknown keys or values other than `yes` and `no`; `Content-Usage:` lines that do not parse |
| `readability.agent-skills` | `/.well-known/agent-skills/index.json` | built files | warning | Index that is not valid v0.2.0; a skill whose `url` is not in the site; a `digest` that does not match the file |
| `readability.api-catalog` | `/.well-known/api-catalog` | built files | warning | Not a linkset (`application/linkset+json` content); links to files that are not in the site |
| `readability.mcp-card` | `/.well-known/mcp/server-card.json`, `/.well-known/mcp.json` | built files | warning | Not valid JSON; no `serverInfo` with `name` and `version`; no transport endpoint |
| `readability.a2a-card` | `/.well-known/agent-card.json` | built files | warning | Not valid JSON; missing required fields of the A2A agent card |
| `readability.markdown-negotiation` | a deployed URL | network, opt-in | warning | The page does not answer `Accept: text/markdown` with Markdown |

Findings of all checks carry `appliesTo: built-output` except `readability.markdown-negotiation`, which reports on the deployed site.

## The score

The report gains a `summary.readability` object when any `readability.*` check ran (task `readability.score`):

```json
{ "readability": { "score": 82, "checks": 11, "passed": 8, "withFindings": 3 } }
```

It is a count, not a quality judgment: the share of applicable checks with no finding, as a whole number 0 to 100. A check that did not apply (no file, no pages of that kind) is not counted. The score never fails a run on its own; severities do that.

## What is out of scope for v1

- Web Bot Auth (`/.well-known/http-message-signatures-directory`), OAuth discovery (RFC 8414, RFC 9728), WebMCP, and the commerce protocols (x402, UCP, ACP). They are runtime or hosting concerns; WebMCP is a rendered check planned separately.
- Judging whether content is good, accurate, or useful to a model.
- Fetching anything from the network, except `readability.markdown-negotiation` when asked.

## Changing this spec

A new check ID, a new optional field, or a stricter severity for a draft that became final is additive and goes in the changelog. Removing a check, raising any check to `error`, or changing what a check ID means needs an RFC, like every other contract.
