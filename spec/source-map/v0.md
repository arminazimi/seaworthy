# Source-map spec, v0 (draft)

**Status:** Draft, 2026-10-20. `spec: 0` is a draft that changes without notice; it freezes as `spec: 1` at `release.contract-freeze`, like the report and config. Task: `spec.source-map`.

This spec defines one published file, `source-map.json`, that a theme or generator may ship with a built site. For a built file — and, where the generator can say so, for a section of it — the file names which source file and line produced it. Its only job is provenance: it lets a tool that has a finding on `/docs/foo/index.html#installation` point an agent at `src/content/docs/foo.md:41` instead of at the built output the agent should not edit. It does not carry content, does not map tokens or bytes, and is not a debugging aid for bundles.

## Principles

1. **Coarse on purpose.** v0 maps a whole file and, optionally, a heading anchor within it, each to a source line. That is the resolution a person editing content works at, and the resolution every generator can reach. Token and byte spans are out of scope (see Source Map v3 below for those).
2. **Locations only, never content.** An entry names paths and line numbers. It never embeds source text, a hash, or a diff. A reader that wants the content opens the file itself.
3. **Advisory, not authoritative.** A mapping is a hint about where a thing probably came from. A consumer must never fail a run, block a deploy, or rewrite a file because of what this file says.
4. **Safe by default.** A source path is refused if it escapes the repository root. Path traversal is the one thing this format must get wrong-proof, and a reader treats it as data, never as a location to open.
5. **Additive and versioned.** The file stamps its contract version in `spec`, the same field the report and history records use. A reader ignores members it does not understand and keeps working.

## The file

A build may publish at most one source-map file, at the site root:

- on disk: `<built root>/source-map.json`
- as a URL: `/source-map.json`

It is UTF-8 JSON. A top-level object with the fields below and nothing else required. Its absence is normal and is not a defect.

## Shape

Every entry maps a published target to a source location. A file with sections has one entry for the file and one per section it can attribute.

```json
{
  "spec": 0,
  "entries": [
    { "target": "docs/foo/index.html", "source": "src/content/docs/foo.md", "line": 1 },
    {
      "target": "docs/foo/index.html",
      "anchor": "installation",
      "source": "src/content/docs/foo.md",
      "line": 41,
      "column": 1
    }
  ]
}
```

A consumer answering a finding at `/docs/foo/index.html#installation` looks for an entry whose `target` is `docs/foo/index.html` and whose `anchor` is `installation`, and reports `src/content/docs/foo.md:41`. With no `anchor` match it falls back to the entry whose `anchor` is absent (the whole-file entry), then to the built-output location. A minimal file may carry only the whole-page entries:

```json
{ "spec": 0, "entries": [ { "target": "index.html", "source": "src/pages/index.astro", "line": 1 } ] }
```

## Fields

| Field | On | Required | Meaning |
| --- | --- | --- | --- |
| `spec` | top level | yes | The contract version this file follows. `0` for this draft. A non-negative integer. |
| `entries` | top level | yes | Array of mapping entries. May be empty. |
| `target` | entry | yes | The built file this entry describes, relative to the site root, forward slashes, no leading `/`, no `.` or `..` segment. |
| `source` | entry | yes | The source file it came from, relative to the repository root that produced the build, forward slashes, no leading `/`, no drive letter, and no `..` that escapes that root. |
| `line` | entry | yes | 1-based line in `source`, using the same 1-based convention as a report finding location. |
| `column` | entry | no | 1-based column in `source`. |
| `anchor` | entry | no | The section's fragment identifier — the part after `#` in the target URL, written without the `#`. Absent means the entry describes the whole file. |

## Identifiers

- **`target`** is a site path, exactly as a report finding's `location.file` is a site path: relative to the built root, forward slashes. It names a file the consumer can find in the built output.
- **`source`** is a repository path, relative to the repository root the build ran in — the same repository-relative convention [ADR 0008](../docs/adr/0008-sarif-locations.md) uses for SARIF `artifactLocation.uri`. It is not a URL and never absolute.
- **`anchor`** is the fragment identifier of a section as it appears in the published URL. The contract does not say how the anchor was generated (a heading slug, a permalink, a CMS id); it only says the value must match the `#fragment` the consumer is looking up. Two entries may share a `target` with different `anchor` values; at most one entry per `target` leaves `anchor` absent.

## Conformance

A file conforms when:

- it is valid JSON, a top-level object, with an integer `spec` and an array `entries`;
- every entry has string `target` and `source`, and integer `line` ≥ 1, each a path in the form above; and
- no `target` or `source` is absolute, contains a backslash, or resolves outside its root.

Beyond that a generator:

- **may** emit any subset of files and sections — entries are best-effort, and leaving a page unmapped is allowed;
- **must** make `target` refer to a file that is present in the built output;
- **should** use one-based line numbers that point at the line a person would edit, not at a template boundary; and
- **must not** rely on a reader acting on the file: every field is advisory.

Unknown members at any level are permitted and are ignored by a conforming reader; this is what lets the contract grow without breaking readers.

## Failure rules

A consumer **must** follow these. Each degrades to today's built-output location, never to a guess and never to a crash.

| Situation | Consumer behaviour |
| --- | --- |
| No `source-map.json` at the site root | Not an error. Use the built-output location, as today. |
| The file is present but not valid JSON | Ignore the whole file; fall back to built output. Never fail the run. |
| `spec` is higher than the reader implements | Read the members the reader understands, ignore the rest, keep working. A newer version is never fatal. |
| An entry is unreadable (missing or wrong-typed required field) | Skip that one entry by name (its `target`, or its index) and keep the others. |
| `source` or `target` is absolute, has a `..` segment, or resolves outside its root | **Refuse the entry.** This is the security rule: a reader never resolves a source path outside the repository root it was given. |
| `source` names a file that is not present | Treat the mapping as stale; never open a missing file as if it were fact — fall back to built output for that finding. |
| `target` names a file that is not in the built output | Ignore it: nothing points there. |

## Relationship to Source Map v3

[Source Map v3](https://sourcemaps.info/spec.html) (the format standardised by Mozilla and Google for JavaScript and CSS) solves the same class of problem — mapping generated output back to the file that produced it — and this contract deliberately does not compete with it. A v3 map is per generated file: it lives beside one minified `app.js`, stores its original positions in a base64 VLQ `mappings` string, and resolves `sources` relative to a single `sourceRoot`/`file` pair. That design is exactly right for a token in a bundle and wrong for what this needs, for three reasons:

1. **No site-wide index.** v3 has one map per output file; there is no plain, human- and agent-readable file that lists provenance across a whole site's pages. This contract is that index.
2. **No document sections.** v3's unit is a character offset between a generated position and an original one. It has no notion of "this `<h2 id="installation">` came from line 41 of the Markdown", which is the resolution content authors and agents work at.
3. **Emitting it is not cheap for markup.** A v3 map requires the transformer to track every byte through the build. An HTML, Markdown, or CMS generator that knows "page X rendered from content Y" can emit a whole-file and per-heading mapping directly, in readable JSON, with no VLQ.

A build may carry both: v3 maps for its JavaScript and CSS, and `source-map.json` for its pages and sections. They do not overlap and neither replaces the other.

## Versioning

The `spec` field is the contract version, stamped and evolved exactly as the report (`spec/report`) and the history record (`packages/verify/src/history.ts`) do: `spec: 0` is this draft; it freezes as `spec: 1` at `release.contract-freeze`. Evolution is additive only — a new optional entry field, a new top-level field readers ignore. Because readers must ignore unknown members, a newer file still reads on an older consumer, and a reader that meets a `spec` greater than it understands reads what it knows and refuses nothing on version alone. Removing a field, changing what a field or an anchor means, or renumbering requires an accepted RFC, like every other contract here.

## What Seaworthy does today

Nothing. No release of Seaworthy reads, writes, or validates `source-map.json`: there is no source-map code in `packages/verify/src` (`grep -rn "source-map\|sourceMap" packages/verify/src` returns nothing), and findings still carry `appliesTo: "built-output"` with the agent doing the translation, per [ADR 0006](../docs/adr/0006-check-model.md) and [ADR 0008](../docs/adr/0008-sarif-locations.md). v0 is a contract a generator may emit and a consumer may build against. Mapping Seaworthy's findings back to source through this file is the separate roadmap task `int.source-map`; a check that validates a published `source-map.json` would be a later, additive task. This spec makes no claim about what the engine does with the file, because today it does nothing.

## What is out of scope for v0

- Token- and byte-level spans, VLQ encoding, and any replacement of Source Map v3 for JavaScript or CSS.
- Multiple source roots, remote or absolute `source` paths, and content hashes or snippets.
- The reader, the report field, and the CLI behavior that will consume this file (`int.source-map`).
- Any Seaworthy check that validates a published source-map file.

## Changing this spec

A new optional field, a new allowed entry, or a clarification that does not change what an existing field means is additive and goes in the changelog. Removing a field, changing what `target`, `source`, `line`, or `anchor` means, tightening a path rule, or bumping the version a reader must reject needs an accepted RFC — the same rule as every other versioned contract in [`spec/`](README.md).
